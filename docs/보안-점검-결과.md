# 보안 점검 결과

점검일: 2026-11-10 · 대상: 코드(커밋 `fd10b20` 이후 변경 포함), 실제 Supabase, Vercel 배포, 의존성

## 결론

**코드와 데이터베이스 권한에서 악용 가능한 취약점은 찾지 못했다.** 아래 3가지는 **사람이 해야 하는 조치**다.

1. **최고 관리자 비밀번호를 강한 것으로 바꾼다.** 채팅에 올라온 값이고, 키보드 배열 형태라 추측하기 쉽다. 로그인 시도 횟수 제한은 Supabase 기본값뿐이라 비밀번호 강도가 사실상 유일한 방어선이다.
2. **Node.js를 수정된 버전으로 올린다** (Node2Shell, CVE-2026-111497). 이 PC는 26.1.0(수정 전). Vercel은 재배포 후 대시보드 "서버 환경" 줄로 확인한다.
3. **최고 관리자를 2명 이상**으로 하고, 가능하면 2단계 인증을 도입한다 (현재 1명, 미사용).

## 최근 취약점 해당 여부

| 취약점 | 해당? | 근거 |
| --- | --- | --- |
| **React2Shell** (CVE-2025-55182, React 서버 컴포넌트 원격 코드 실행) | **아니오** | 영향 범위: Next.js 15.0.0–16.0.6, React 19.0.0·19.1.0·19.1.1·19.2.0. 이 프로젝트는 **Next.js 16.4.5 / React 19.3.1** (수정 버전 16.0.7·19.2.1 이상) |
| **Node2Shell** (CVE-2026-111497, Node.js Brotli 해제 오류) | **런타임 패치 필요** | 우리 코드·의존성은 압축 해제를 직접 쓰지 않고 `brotli` 패키지도 없다. 원격에서 공격 가능한 경로는 (1) 공격자가 만든 요청 본문을 푸는 코드(해당 없음) (2) 서버가 받는 `fetch` 응답(우리는 Supabase 응답뿐, HTTPS) (3) Next 이미지 최적화로 가져오는 외부 이미지(외부 주소 허용 목록 없음, 해당 없음). 실제 위험은 낮지만 **수정 버전이 나와 있어 올리는 것이 정답**이다 |

## 점검한 것과 결과

### 인증·권한
- 공개 통로가 되는 서버 동작(Server Action) **모두 인증 검사가 있다.** 각 동작이 직접 확인하므로 다른 경로로 호출해도 우회되지 않는다.
- 로그인 실패 문구가 같아 **계정 존재 여부가 드러나지 않는다.** 비밀번호 찾기도 항상 같은 안내.
- 로그인 후 이동 주소는 `/admin…`만 허용 (열린 이동 없음).
- 비활성 계정은 다음 요청부터 차단. 활성 최고 관리자 0명이 되는 변경은 DB가 거부.

### 데이터베이스 (실제 Supabase에서 로그인하지 않은 외부인으로 시험, 44건 모두 통과)
- 프로필·수정 기록 읽기 차단, 임시 저장·휴지통 글·숨김 항목·동의 없는 사진은 보이지 않음
- 글·주보·설교·배너·FAQ·예배·공동체·첨부·수정 기록·프로필 **만들기 차단**, 수정·삭제 차단, 권한 상승 시도 차단
- 관리 함수 4개 호출 차단, 저장소 4곳 업로드·목록 열람 차단, API 구조(OpenAPI) 열람 차단(401)
- 시험은 서버 키로 만든 `[SEC]` 행만 대상으로 했고 끝나고 모두 지웠다.
- ※ 콘텐츠 담당자와 최고 관리자 사이의 권한 경계는 로컬 모의 DB 테스트로만 확인했다 (담당자 계정이 아직 없음).

### 입력·화면
- `innerHTML`·`eval` 등 위험한 코드 없음. 링크 주소(신청·영상·지도·채널)는 http(s)만 허용, `javascript:` 차단(테스트 있음)
- 파일 업로드: 형식·크기를 브라우저와 저장소 설정이 이중으로 제한, HTML·SVG·스크립트 형식 없음, 저장 위치는 UUID 형식만 인정

### 비밀 값
- 코드, **변경 기록 4개 커밋 전체**, 올라간 파일에서 키·토큰·프로젝트 식별자·비밀번호·실제 이메일 **0건**
- 실제 키로 빌드한 결과물에서 **서비스 키가 브라우저용·서버용 파일 어디에도 없음** (공개용 anon 키만 브라우저에 있음, 설계대로)
- `.env.local`, 로그인 세션, 촬영 영상, 오래된 `bun.lock`은 저장소에서 제외

### 의존성
- 운영 코드 **취약점 0건** (`npm audit --omit=dev`). 개발 도구 `minimatch` 1건(중간)만 상위 패키지가 고칠 때까지 남음 — 개발 PC에서만 쓰이고 위험한 입력이 없다.
- Vercel이 오래된 `bun.lock`(Next 15.5.29, zod 3 등 취약 버전 고정)을 따르지 않도록 저장소에서 뺐다.

### Supabase 설정
- 공개 가입 차단, 이메일 자동 확인 꺼짐, 로그인 방식은 이메일만
- 저장소 4곳: 형식 제한(위험 형식 없음), 크기 제한 있음. 공개 버킷이지만 파일 주소가 UUID라 추측 불가

### 배포 (Vercel)
- HSTS(2년, preload), 클릭재킹 방지, MIME 추측 방지, 참조 주소 제한, 기기 권한 차단 정상. 관리자 화면은 캐시되지 않음. 미리보기 주소는 Vercel 로그인 보호.

## 이번 점검에서 고친 것

| 내용 | 효과 |
| --- | --- |
| **콘텐츠 보안 정책(CSP)과 COOP 헤더 추가** (`lib/csp.ts`) | 악성 스크립트가 끼어들어도 로그인 토큰을 다른 사이트로 보내지 못하게 접속처를 이 사이트와 Supabase로 제한. 방문자·관리자 흐름(파일 업로드, PDF 미리보기 포함)을 실제로 돌려 **CSP에 막힌 요청 0건** 확인 |
| **로그인 쿠키 강화** (`lib/supabase/cookies.ts`) | 운영(https)에서 `Secure`, 유효기간 **400일 → 7일**(사용 중에는 갱신) |
| **Node.js 패치 점검** (`lib/node-security.mjs`) | `npm run dev` 때 수정 전 Node면 경고, 관리자 대시보드에 서버 Node 버전과 패치 여부 표시 |
| 관리자 "홈페이지 보기" 링크에 `noopener` | 새 창 보안 |
| 배포 점검 스크립트 `npm run check:deploy` | 배포 후 환경 변수·주소·헤더·CSP를 한 번에 점검 |

## 남은 위험과 권고

| 중요도 | 내용 | 권고 |
| --- | --- | --- |
| **높음** | 최고 관리자 비밀번호가 약하고 채팅에 노출됨 | 지금 강한 비밀번호(긴 문장형)로 변경 |
| **높음** | Node 런타임 수정 전 버전(이 PC), Vercel 반영 미확인 | Node 업데이트, 재배포 후 대시보드 확인 |
| 중간 | 최고 관리자 1명, 2단계 인증 없음 | 2번째 관리자 초대. 2단계 인증(Supabase TOTP) 화면은 아직 없음 — 필요하면 추가 개발 |
| 중간 | Vercel Preview에 비밀 키가 들어가면 검토 전 코드가 사용 가능 | 비밀 키는 **Production 환경에만** (배포 가이드 참고) |
| 중간 | 공개 저장소: DB 구조·권한 규칙(SQL)과 시안 사진 2장이 공개됨 | 구조 공개는 RLS 설계상 문제 아님. 사진 사용 권한 확인, 원하면 저장소를 비공개로 |
| 낮음 | 로그인 쿠키가 httpOnly가 아님 | 브라우저에서 직접 파일을 올리는 구조 때문. CSP로 보완 |
| 낮음 | 방문자 화면 CSP 스크립트에 `unsafe-inline` 허용 | **관리자 화면(`/admin`)은 요청마다 새 nonce만 허용하는 엄격 CSP로 해결**(운영 빌드에서 위반 0건 확인). 방문자 화면은 정적 캐시를 지키려고 유지하고 외부 접속 제한으로 보완 — 로그인 토큰이 있는 곳은 관리자 화면이다 |
| 낮음 | 로그인 시도 제한이 Supabase 기본값뿐 | 비밀번호 강도와 2단계 인증이 실질 방어 |
| 낮음 | 관리 함수(RPC)를 로그인 없이 호출은 가능(권한 오류로 거부됨) | 원하면 실행 권한 회수 SQL을 추가 가능. 현재도 안전 |
| 낮음 | 메일 링크의 토큰(`#access_token`) 처리 화면 | 공격자가 자기 계정 토큰을 링크로 심어 로그인시킬 수 있으나, 관리자 권한 계정이어야 의미가 있어 사실상 해당 없음 |

## 다시 점검하려면

```bash
npm audit --omit=dev            # 의존성
npm run check:node              # Node 패치
npm run check:deploy -- <주소>   # 배포된 사이트
npm test                        # 권한(RLS)·검증 테스트 136건
```

배포 전과 의존성·Node를 올릴 때마다 실행한다. 새 Node 취약점이 공지되면 `lib/node-security.mjs`의 표에 줄을 더한다.
